# Operating exam and no-exam admissions

The portal supports two admissions paths in the same installation. Registration,
scholarship review, payment documents and staff payment verification are shared.
Scholarship refusal **ends the application in both modes**. There is no conversion
to a normal ticket after refusal.

## Configuration and account behavior

Superusers can change the default mode on **Admissions settings** (staff home) or
in **Django admin → Constance → Config**. Ordinary staff can review scholarships
and payments, but cannot change these settings.

| Setting | Meaning |
| --- | --- |
| `ADMISSIONS_MODE` | `exam` or `no_exam`; copied onto each new signup. Defaults to `exam`. |
| `ADMISSIONS_ASK_ATTENDANCE_PREFERENCE` | Defaults to true. Show and require the attendance survey in either mode; false hides it and removes that prerequisite. Existing answers are preserved and unanswered fields stay blank. |
| `ACCOUNT_ALLOW_REGISTRATION` | Master switch for new signups in either mode. |
| `NO_EXAM_REGISTRATION_OPEN` | Allows new no-exam signups and completion of their registration steps. Closing it does not block existing payment or scholarship review. Defaults to false. |
| `NO_EXAM_ACADEMY_ACCESS_OPEN` | Allows enrolled no-exam students to access course content on/after `ACADEMY_START`. Defaults to false. |
| `ACADEMY_START` | Earliest no-exam course access date; also the legacy exam calendar's academy phase date. |
| `ADMISSIONS_PAYMENT_DAYS` | Days from issuing/resetting payment instructions to payment deadline; default 7. Changing this does not rewrite existing deadlines. Must be positive. |
| `ADMISSIONS_ACCEPTING_PAYMENT_PROFS` | Allows candidate document uploads/submission. Staff can still review previously submitted documents when this is off. |
| `PORTAL_STATUS` | Legacy exam calendar: `admissions`, `admissions:applications`, `admissions:selection`, `academy`. The scheduler maintains it. It does not close shared admissions pages. |
| `ADMISSIONS_APPLICATIONS_START`, `ADMISSIONS_SELECTION_START`, `ADMISSIONS_CODING_TEST_DURATION` | Existing exam window and coding test timer. Exam signups close at the selection start. |

An account keeps its saved `User.admissions_mode` when the default changes. All
existing accounts migrate to `exam`, with no changes to application outcomes,
payments, or student status. The migration does not send email. Old scholarship
decision metadata is not reconstructed; pre-existing records retain their original
selection status and logs, and receive decision metadata when subsequently reviewed.

This remains a portal with one active course/batch configuration. The toggle does
not add cohort history or support enrolling the same account again in a second
batch. Keep the existing process for preparing a new edition's course data and
accounts. Do not assume changing the default reassigns an existing account.

## Deploying this change

1. Back up the database and uploaded documents using the existing deployment procedure.
2. Stop the old scheduler while rolling out the new application. Its old code can
   close the master signup switch when the exam deadline passes.
3. Apply the migrations using the updated application:

   ```sh
   cd portal
   poetry run python manage.py migrate
   poetry run python manage.py check
   ```

   The normal production and development web startup scripts already run migrations.
   Apply them before routing requests to the updated application. No production
   migration is performed merely by changing files in this checkout.
4. Run the updated scheduler continuously:

   ```sh
   poetry run python manage.py run-scheduler
   ```

   Docker Compose supplies a separate scheduler service with the same environment
   file as Django. The Helm Deployment includes an `admissions-scheduler` sidecar
   using the Django image and environment. For other deployment methods, supervise
   this command alongside the web process. It updates the exam calendar and sends
   queued enrollment notifications. It retries if migrations are not yet ready.
5. Verify the existing Elastic Email **Admissions - generic message** template
   displays its `message` merge field. The new enrollment emails use this existing
   template with text defined in `selection/enrollment.py`; the backend escapes
   that text before inserting it into the template. Signup now also uses **Admissions - generic message**, with a
   mode-neutral confirmation link generated by the portal. Check externally hosted email wording and Wiki
   admissions pages for references to exams or the old 48-hour deadline.
6. Exercise a real signup, email confirmation, the enabled registration steps,
   scholarship decisions and payment verification in staging. Do not use
   `create-student` to test admissions: that helper creates an already-authorized
   student and bypasses the application workflow.

The enrollment outbox is visible in Django admin under **Enrollment emails**.
Changes and their notification records commit in one database transaction. Failed
sends retry with increasing delay, up to one hour. Multiple scheduler workers use
row locks to avoid sending the same pending record concurrently. Delivery is
at-least-once: a crash after the provider accepts a message but before the database
records success can produce a duplicate. No production email delivery is implied
by successful tests using Django's in-memory backend.

## Scheduled no-exam intake

For the 2026/27 calendar, S01 progression rules, audited deadline exceptions and
rollout procedure, see [edition-2026.md](edition-2026.md).

| Setting | Scheduled behavior |
| --- | --- |
| `NO_EXAM_USE_SCHEDULE` | Enable date windows in addition to manual switches. Default false preserves existing manual operation. |
| `NO_EXAM_SIGNUPS_START` | Inclusive opening for new accounts and registration steps. |
| `NO_EXAM_SIGNUPS_END` | Exclusive closing for new accounts only. |
| `NO_EXAM_REGISTRATION_END` | Exclusive closing for existing applicants' steps. |
| `NO_EXAM_PAYMENTS_START`, `NO_EXAM_PAYMENTS_END` | Inclusive opening/exclusive closing for candidate document submission; staff review remains available. |

When scheduling is enabled, no-exam payment instructions use the fixed edition
payment cutoff instead of `ADMISSIONS_PAYMENT_DAYS`. The exam workflow retains
its per-applicant payment period. `ADMISSIONS_APPLICATIONS_START` and
`ADMISSIONS_SELECTION_START` do not control scheduled no-exam signup.

## Opening a manual no-exam intake

1. Set `ACADEMY_START` to the correct course start date. Keep
   `NO_EXAM_ACADEMY_ACCESS_OPEN=False` until course access should open.
2. Select **No exam** as the default admissions mode.
3. Enable `ACCOUNT_ALLOW_REGISTRATION` and `NO_EXAM_REGISTRATION_OPEN`.
4. Enable `ADMISSIONS_ACCEPTING_PAYMENT_PROFS` and verify the payment deadline
   length. Fees remain €250 student, €500 regular, €1500 company and €20 for an
   approved scholarship, as defined in `selection/payment.py`.
5. Applicants sign up and follow the confirmation link in their email. A reply to
   an email does not set the portal's verified-email state. They accept the code of
   conduct/refund policy, make a final scholarship choice, and, when the survey is enabled, choose attendance
   preference. The final step automatically completes registration if their
   required profile fields and verified email are present. No challenge records,
   admission notebooks or admission grading service are required for this path.
6. Non-scholarship applicants immediately receive payment instructions. Scholarship
   applicants appear in **Scholarships** for staff review. Approval issues the
   scholarship payment instructions. Refusal closes admission and does not issue
   normal-ticket payment instructions.
7. Applicants upload payment proof, plus student ID for a student ticket, and click
   **Submit payment proof**. Staff verify it under **Payments**. They can request
   additional proof, refuse it (ending admission), or accept it. Acceptance grants
   no-exam student status immediately and initializes attendance records for the
   existing hackathons. An additional **End Admissions** event is not required.
8. Enable `NO_EXAM_ACADEMY_ACCESS_OPEN` when appropriate. Course access also waits
   for `ACADEMY_START`; the profile requires GitHub and Slack details for the normal
   course views. No-exam students remain able to view admissions/payment pages.

Closing new signups does not close an existing applicant's registration
steps. Close `NO_EXAM_REGISTRATION_OPEN` separately when needed. Scholarship and
payment processing remain available after either switch is closed.

Staff can reset payment instructions only while an applicant is awaiting documents,
with an explicit reason. Non-scholarship ticket corrections happen through that
staff action; applicants cannot change a frozen price through their profile.
Already accepted/rejected applications cannot be reopened through payment reset,
a duplicate submission, or repeated scholarship decisions.

## Returning to exam admissions

1. Prepare the existing admission challenges (`coding_test`, `slu01`, `slu02`,
   `slu03`), downloads/checksums, grader service/image and course data for the edition.
2. Set the application opening/closing dates, coding test duration and academy start
   date in chronological order, then select **Exam** and enable new signups.
3. New applicants still verify email and complete the enabled registration steps. They then
   complete the admission tests. After the window closes, superusers use **Exam
   events → End Applications** to produce test outcomes. Staff use **Exam selections**
   for the existing draw and selection process.
4. Review selected scholarships and payments through the shared staff pages.
   Accepting exam-applicant payment retains the old behavior: it records acceptance
   without setting student status. **End Admissions** grants student status once
   pending exam selections are resolved. No-exam applications do not enter the draw
   or affect that event's pending-count checks.

Changing the default to Exam does not stop pending no-exam payments. Changing it to
No exam does not cancel existing exam applicants or their grader callbacks.

## Existing untouched accounts

If an account was created before deployment and has not started admissions, an
operator may explicitly change its saved mode:

```sh
poetry run python manage.py set-admissions-mode --user applicant@example.com --mode no_exam
# Inspect the dry-run result, then explicitly apply:
poetry run python manage.py set-admissions-mode --user applicant@example.com --mode no_exam --apply
```

The command refuses staff, instructor or student accounts; accepted policies,
scholarship decisions, attendance preferences, completed registration, selections,
exam timers, recorded exam results or submissions also prevent conversion. An empty
`Application` created by the old homepage GET alone does not prevent conversion.
Active applications require a separately reviewed migration; never bulk-switch them
with a database update. To switch future intakes, change the default, not the schema.
Do not roll back these migrations once no-exam applications exist without a data
migration plan: their mode and notification/decision metadata would be lost.

## Verification

Run `poetry run pytest` with the project's test settings and a disposable PostgreSQL
database. The admissions tests cover signup/email verification, the three forms,
both workflow paths, scholarship refusal, document privacy, payment state guards,
exam callbacks and legacy events, course access, outbox retries, concurrent requests,
pristine-account conversion and upgrading populated legacy records. Tests do not
contact Elastic Email or invoke an external grader.

## Optional attendance survey

Change `ADMISSIONS_ASK_ATTENDANCE_PREFERENCE` in **Django admin → Constance → Config**.
It is independent of the default admissions mode and applies to both workflows.
When disabled, the exam becomes step 3; no-exam registration has only steps 1–2.
Existing unfinished no-exam applicants who already completed those steps can use
**Complete registration** on their home page, while registration remains open.
No bulk enrollment or email sending occurs merely by changing the switch.
Direct survey visits redirect home while disabled, and survey writes are rejected.

Re-enabling requires an answer from unfinished applicants. Registrations already
completed (including legacy selected applicants and enrolled students) keep their
validity even if the preference is blank; payments and exam/course access are not
revoked by this switch. All other eligibility, date and payment checks still apply.
No database migration or replacement preference values are needed.
